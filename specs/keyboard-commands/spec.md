# Keyboard Commands Specification

## Overview

This specification defines the keyboard command system for Wrangle: a central command registry, keyboard-binding presets (built-in + user), scope-aware dispatch (Monaco editor vs global window), markdown formatting commands, WYSIWYG preview-selection editing, and the Preferences → Keyboard Shortcuts tab used to customize bindings.

**Feature Prefix:** `KBD` (Keyboard Commands)

---

## Requirements

### KBD-001: Command Registry Shape

- **Status:** Active
- **Added:** 2026-04-23
- **Updated:** 2026-04-28 (replaced `readOnly` / `bindingDisplay` with `bindingShape`; see `all-shortcuts-editable` plan)

Every user-invocable action in the app is declared as a `CommandDefinition` entry in a single registry (`src/renderer/src/commands/registry.ts`). The registry is the single source of truth for command identity, label, category, and default binding.

**Behavior:**
- Each command has a stable `id` (dot-namespaced, e.g. `markdown.bold`, `file.save`), a human-readable `label`, a `category` (`file | edit | view | navigation | markdown | app`), a `defaultBinding` (accelerator string such as `Ctrl+B`, modifier-only string such as `Ctrl`, or `null`), and an `execute(ctx: CommandContext)` function.
- A command may declare `bindingShape: { suffix: 'Scroll' | 'Drag' | 'Tap' }` to indicate its key binding is a bare modifier completed by a fixed mouse/tap gesture. The user-editable portion is the modifier; the suffix is fixed by code (e.g. `view.zoomScroll` defaults to `Ctrl` + Scroll).
- A `commandMap: Map<string, CommandDefinition>` and `getCommandsByCategory(category)` helper are exported for lookup and grouping.
- Command IDs are permanent. Renaming a command requires deprecating the old ID and introducing a new one; silent ID changes break persisted user presets.

**Interface Contract:**
```ts
interface CommandDefinition {
  id: string
  label: string
  category: CommandCategory
  defaultBinding: string | null
  execute: (context: CommandContext) => void
  bindingShape?: { suffix?: 'Scroll' | 'Drag' | 'Tap' }
}
interface CommandContext {
  editor: monaco.editor.IStandaloneCodeEditor | null
  dispatch: (action: unknown) => void
  getState: () => unknown
  previewSelection?: { start: number; end: number } | null
  targetTabId?: string
  handlers: {
    onFileNew; onFileOpen; onFileSave; onFileSaveAs; onCloseTab;
    onEditUndo; onEditRedo; onOpenPreferences; onOpenFolder
  }
}
```

### KBD-002: Built-in "default" Preset Is Immutable (Auto-Forks on Edit)

- **Status:** Active
- **Added:** 2026-04-23
- **Updated:** 2026-04-28 (semantics changed: edits to a built-in preset auto-fork to a custom preset; see KBD-012)

A built-in preset named `default` is derived at load time from every command's `defaultBinding`. The built-in itself is immutable, but editing while it is active silently forks it to a new custom preset (KBD-012) — the user does not need to discover or click "Copy to Custom" first.

**Behavior:**
- `builtInPresets.default` is generated by iterating the command registry and collecting `{ [cmd.id]: cmd.defaultBinding }` for every command (including `bindingShape.suffix` commands, whose defaults are bare modifier strings).
- When `shortcuts.currentPreset` names a built-in preset, the Shortcuts tab no longer displays a read-only notice and recorders are no longer disabled. Edits go through `editShortcutBinding` (KBD-012), which creates a custom preset and switches to it before applying the edit.
- The `default` preset is always available in the preset selector for "restore defaults" purposes.
- New commands added to the registry in future releases automatically appear in the `default` preset on next launch without migration.

**Interface Contract:**
- `builtInPresets: Record<string, ShortcutBindings>` in `settingsSlice.ts`
- `selectCurrentBindings` returns from `builtInPresets` when the current preset is built-in
- `editShortcutBinding({ commandId, shortcut })` thunk performs the auto-fork (KBD-012)

### KBD-003: User Preset CRUD

- **Status:** Active
- **Added:** 2026-04-23

Users can create, duplicate-from-current, rename (via duplicate + delete), delete, and switch between custom presets. Custom presets persist via `electron-store`.

**Behavior:**
- "Copy to Custom" captures the currently active bindings (built-in or custom) and saves them as a new custom preset under a user-supplied name, then activates that new preset.
- Preset names must be unique across `builtInPresets` and `shortcuts.customPresets`; attempting to create a duplicate shows an alert and the modal stays open.
- Deleting the currently active custom preset resets `shortcuts.currentPreset` to `default`.
- Custom presets are stored in `SettingsState.shortcuts.customPresets: Record<string, ShortcutBindings>` and persisted by `saveShortcutSettings` (debounced 1000ms).
- A binding within a custom preset may be `null` to indicate "unbound"; a null binding is never dispatched.

**Interface Contract:**
- Redux actions: `setCurrentPreset`, `addCustomPreset`, `updateCustomPreset`, `updateShortcutBinding`, `deleteCustomPreset`
- Thunk: `saveShortcutSettings()` reads the current `shortcuts` substate via `getState` and persists it (no payload argument — avoids stale-closure races when the caller debounces)
- Selector: `selectAllPresetNames(state): string[]` returns built-in names followed by custom names

### KBD-004: Editor-Scoped vs Global-Scoped Dispatch

- **Status:** Active
- **Added:** 2026-04-23

`useKeyboardShortcuts` routes each command to either Monaco's action registry or a window-level keydown listener based on an explicit scope list, so bindings work whether or not the editor has focus.

**Behavior:**
- For each command with a non-null current binding, the hook attempts to register a Monaco action via `editor.addAction({ id, label, keybindings, run })` using `parseShortcutToMonaco(binding)`.
- Commands in the `globalCommands` list (file.*, app.preferences, view.devTools, view.outline, view.explorer, view.toolbar, nav.nextTab, nav.prevTab, nav.nextWorkspace, nav.prevWorkspace) are excluded from Monaco registration and are instead matched against window `keydown` events via `matchesShortcut(event, binding)`.
- When focus is inside an `INPUT`, `TEXTAREA`, or `contentEditable` element, only the `allowInInput` allowlist fires (save/open/new/preferences and all markdown formatting commands). All other global shortcuts are suppressed in those targets.
- All Monaco disposables are tracked in `disposablesRef` and disposed on re-registration or unmount.
- The hook re-registers when `bindings` changes so that switching presets takes effect immediately without reload.

**Interface Contract:**
- `useKeyboardShortcuts({ editorRef, handlers, previewSelection })` returns `{ executeCommand, bindings }`
- `parseShortcutToMonaco(binding: string): number | null`
- `matchesShortcut(event: KeyboardEvent, binding: string): boolean`

### KBD-005: Markdown Formatting Commands

- **Status:** Active
- **Added:** 2026-04-23

The registry defines a complete set of markdown formatting commands that operate on the active Monaco selection.

**Behavior:**
- Inline-wrap commands (`markdown.bold` → `**...**`, `markdown.italic` → `*...*`, `markdown.strikethrough` → `~~...~~`, `markdown.code` → `` `...` ``) wrap the selection via `applyMarkdownFormat(editor, prefix, suffix, previewSelection)`. If no text is selected, markers are inserted and the cursor is placed between them.
- Line-prefix commands (`markdown.heading1..6`, `markdown.bulletList` → `- `, `markdown.numberedList` → `1. `, `markdown.taskList` → `- [ ] `, `markdown.blockquote` → `> `) call `applyLinePrefix`, which prepends the prefix to every line covered by the selection (start line through end line inclusive).
- `markdown.link` wraps the selection as `[text](url)`; when no text is selected, the cursor is placed on the placeholder `link text`.
- `markdown.codeBlock` wraps the selection in a triple-backtick fenced block and positions the cursor on the opening-fence language slot.
- `markdown.table`, `markdown.image`, and `markdown.hr` use `insertText` to insert a template at the cursor.
- Default bindings: Bold `Ctrl+B`, Italic `Ctrl+I`, Strikethrough `Ctrl+Shift+X`, Code `` Ctrl+` ``, Link `Ctrl+K`, Headings `Ctrl+Alt+1..6`, Bullet `Ctrl+Shift+8`, Numbered `Ctrl+Shift+7`, Task `Ctrl+Shift+9`, Blockquote `Ctrl+Shift+.`, Code Block `` Ctrl+Shift+` ``. Table/Image/HR have no default binding.

**Interface Contract:**
- Helpers in `registry.ts`: `applyMarkdownFormat`, `applyLinePrefix`, `insertText`
- All markdown commands read `ctx.editor` and `ctx.previewSelection`

### KBD-006: WYSIWYG `applyPreviewSelection` Path

- **Status:** Active
- **Added:** 2026-04-23

When the user has a text selection inside the rendered preview pane, markdown formatting commands re-target the editor selection to the underlying source range before applying formatting.

**Behavior:**
- Every markdown command helper calls `applyPreviewSelection(editor, previewSelection)` as its first step.
- `applyPreviewSelection` converts `{ start, end }` character offsets to Monaco `Position`s via `model.getPositionAt` and calls `editor.setSelection(...)` to mirror the preview selection into the editor.
- A `null` or `undefined` `previewSelection` is a no-op; the current editor selection is used unchanged.
- After re-selection, `applyMarkdownFormat` / `applyLinePrefix` / `insertText` operate on the editor as in KBD-005, so formatting applied via the preview is indistinguishable from formatting applied in the editor.
- The preview selection is threaded through `useKeyboardShortcuts` via the `previewSelection` option and attached to every `CommandContext` produced by `getCommandContext`.

**Interface Contract:**
- `useKeyboardShortcuts({ ..., previewSelection })`
- `CommandContext.previewSelection?: { start: number; end: number } | null`
- Private helper `applyPreviewSelection(editor, previewSelection)` in `registry.ts`

### KBD-007: Menu Accelerators Reflect Active Preset

- **Status:** Active
- **Added:** 2026-04-23
- **Updated:** 2026-04-28 (implementation landed; menu schema externalized; see KBD-013)

The native application menu's accelerator labels are driven by the currently active preset, not hardcoded.

**Behavior:**
- The native menu is built from a JSON-serializable schema (`src/shared/menu-schema.ts`) where each interactive node references a registry `commandId`. The main process resolves accelerators by looking up the active preset bindings.
- When the renderer's active bindings change (preset switch, edit, or initial load), the renderer publishes them to main via `window.electron.shortcuts.publishBindings(bindings)` → `shortcuts:bindings-updated` IPC. Main rebuilds the menu via `createApplicationMenu(win, bindings)` (Electron's `Menu.setApplicationMenu` replaces the existing menu wholesale).
- Commands with a `null` binding in the active preset render no accelerator in the menu.
- Menu click handlers emit the registry command ID (KBD-013), which the renderer routes through `commandMap.get(id).execute(ctx)` — identical behavior to keyboard dispatch.
- Commands with `bindingShape.suffix` (Scroll/Drag/Tap) do not appear as menu accelerators (they're not chord-style shortcuts).

**Interface Contract:**
- `src/shared/menu-schema.ts` exports `menuSchema: MenuNode[]`
- `createApplicationMenu(mainWindow, bindings: Record<string, string | null>)` in `src/main/menu/menu-template.ts`
- IPC: `window.electron.shortcuts.publishBindings(bindings)` (renderer → main on `shortcuts:bindings-updated`)
- The renderer's store subscribes to settings changes and republishes bindings whenever the active preset's bindings change

### KBD-008: Preferences → Keyboard Shortcuts Tab Lists All Commands

- **Status:** Active
- **Added:** 2026-04-23
- **Updated:** 2026-04-28 (Mouse Gestures sub-section; read-only notice removed)

The Keyboard Shortcuts tab enumerates every command in the registry, grouped by category, with the current binding from the active preset shown next to each.

**Behavior:**
- Commands are grouped in the order `file, edit, view, navigation, markdown, app` using `categoryLabels` as group headers.
- Within each category, commands with `bindingShape.suffix === 'Scroll' | 'Drag'` are grouped under a "Mouse Gestures" sub-header.
- A search box filters by `label`, `id`, current `binding` string, or `bindingShape.suffix` (case-insensitive substring); empty groups are omitted.
- Each row displays the command label and a `ShortcutRecorder` (in `chord`, `modifier-only`, or `tap` mode based on `bindingShape`) plus a static suffix label (`+ Scroll`, `+ Drag`, `(tap)`) when applicable, plus a clear button.
- A preset selector lists all preset names with a `(built-in)` suffix for built-ins; a "Copy to Custom" button creates a named editable preset (KBD-003); a "Delete" button appears only for custom presets.
- Built-in presets are no longer displayed as read-only — edits silently fork to a custom preset (KBD-002, KBD-012).
- A Vim Mode checkbox is rendered in this tab and toggles `settings.editor.vimMode` via `setVimMode` + `saveEditorSettings`.

**Interface Contract:**
- Component: `src/renderer/src/components/Preferences/KeyboardShortcutsTab.tsx`
- Consumes: `selectCurrentBindings`, `selectAllPresetNames`, `selectVimMode`, `commands`, `categories`, `categoryLabels`, `commandMap`, `editShortcutBinding`

### KBD-009: ShortcutRecorder Live Capture, Escape Cancel, Conflict Surfacing

- **Status:** Active
- **Added:** 2026-04-23

`ShortcutRecorder` captures a single live keystroke and binds it to the selected command. Escape cancels. Conflicts with existing bindings in the same preset are surfaced before the change is committed to persistence.

**Behavior:**
- Clicking the recorder (when not `disabled`) enters recording mode and focuses the button.
- While recording, a window-level `keydown` capture listener runs; modifier-only presses (`Control`, `Shift`, `Alt`, `Meta`) are ignored.
- `Escape` exits recording without changing the binding and invokes `onCancel`.
- Any other keypress is formatted via `formatKeyboardEvent(e)`, normalized via `normalizeShortcut`, validated via `isValidShortcut`; if invalid, `pendingShortcut` is shown and recording continues; if valid, `onChange(normalized)` is called and recording exits.
- Clicking outside the recorder while recording also cancels.
- After `onChange` dispatches `updateShortcutBinding`, the parent recomputes conflicts via `findConflicts(binding, bindings, commandId)`; any command whose current binding has ≥1 conflict is rendered with the `conflict` CSS modifier on its recorder, surfacing the clash to the user before the 1000ms debounced save fires.
- The recorder's visible label is `"Press keys..."` (or the in-progress invalid `pendingShortcut`) while recording, the current binding string when bound, and `"Unbound"` when `null`.

**Interface Contract:**
- `ShortcutRecorder` props: `{ value: string | null; onChange: (s: string | null) => void; onCancel: () => void; hasConflict?: boolean; disabled?: boolean }`
- `findConflicts(binding, bindings, excludeId): string[]` in `utils/shortcut-parser.ts`
- `formatKeyboardEvent`, `normalizeShortcut`, `isValidShortcut` in `utils/shortcut-parser.ts`

### KBD-010: Reset-Command and Reset-Preset to Defaults

- **Status:** Active
- **Added:** 2026-04-23

Users can restore individual command bindings or an entire custom preset to the registry's `defaultBinding` values.

**Behavior:**
- Reset-command: applying the reset action to a single command in the active custom preset dispatches `updateShortcutBinding({ presetName, commandId, shortcut: commandMap.get(commandId).defaultBinding })`. If the default is `null`, the binding becomes `null` (unbound).
- Reset-preset: applying reset to the whole active custom preset replaces its `bindings` with a fresh copy of `builtInPresets.default` via `updateCustomPreset`.
- Reset actions are disabled (hidden or no-op) when the active preset is built-in, since built-ins already equal the defaults (KBD-002).
- Both reset paths go through the same debounced `saveShortcutSettings` as regular edits (KBD-003), so the change persists within 1000ms.
- Clearing a shortcut via the `×` button in the Shortcuts tab is not a reset; it sets the binding to `null` regardless of the command's default.

**Interface Contract:**
- Redux actions: `updateShortcutBinding` (per-command reset), `updateCustomPreset` (full-preset reset)
- Source of defaults: `commandMap.get(id).defaultBinding` and `builtInPresets.default`

### KBD-011: Markdown Format Toolbar Tap-Alt Trigger

- **Status:** Active
- **Added:** 2026-04-23
- **Applies to:** wrangle
- **Test category:** manual

A command `markdown.openFormatToolbar` opens the floating markdown format toolbar anchored to the current editor caret. Its trigger is a bare **Alt** tap — `keydown(Alt)` followed by `keyup(Alt)` within 500ms with no intervening key, mouse input, or window-blur event. The command appears in the Keyboard Shortcuts tab under the Markdown category with `bindingDisplay: "Alt"` and is `readOnly` (not user-rebindable via the binding system). The legacy floating "+" dot trigger is removed; clicking in empty editor space no longer surfaces any UI.

**Behavior:**
- Tap Alt (no other key, ≤500ms) → `floatingToolbarBus.openAtCursor()` is invoked. `FloatingToolbar` computes the cursor rect via `getMonacoCursorRect`, sets `selectionSource = 'editor'`, `state = 'toolbar'`, and positions the toolbar at the caret.
- Alt+<any key> (e.g. Alt+F, `Ctrl+Alt+1..6`) — does NOT trigger the toolbar. The normal chord dispatcher handles those bindings.
- Holding Alt past 500ms, pressing then releasing Alt after a mouse click, or losing window focus mid-press — all cancel the candidate; no toolbar.
- `preventDefault()` is called on the triggering `keyup(Alt)` to suppress Electron's default Alt-focuses-menu-bar behaviour.
- Selection-based toolbar behaviour (text selected in editor or preview → toolbar appears over the selection) is unchanged by this requirement.
- On non-markdown files, `FloatingToolbar` early-returns; tap-Alt is a no-op.

**Interface Contract:**
- Command: `{ id: 'markdown.openFormatToolbar', category: 'markdown', defaultBinding: null, readOnly: true, bindingDisplay: 'Alt', execute: () => floatingToolbarBus.openAtCursor() }`
- Bus module: `src/renderer/src/components/UI/floating-toolbar-bus.ts` — `{ openAtCursor(): void; subscribe(l: () => void): () => void }`
- Tap-Alt detection lives in `useKeyboardShortcuts.ts` as a dedicated `useEffect` (separate from the chord-dispatch path because `defaultBinding: null` means the binding-lookup path would never fire).

**Verification (manual):**
1. Open a `.md` file; click in empty space inside the editor → no "+" dot appears.
2. Tap Alt (no other keys) → markdown format toolbar appears anchored to the caret.
3. Hold Alt, press F → toolbar does NOT appear; any `Alt+F` binding (if bound) fires normally.
4. Select text → selection-based toolbar still appears above the selection.
5. Preferences → Keyboard Shortcuts → Markdown category: "Open Format Toolbar at Cursor" is listed with the configured modifier and `(tap)` suffix; it is editable (KBD-014).
6. Open a non-markdown file (e.g. `.txt`) → tap Alt does nothing (no toolbar).

### KBD-012: Auto-Copy On First Edit

- **Status:** Active
- **Added:** 2026-04-28
- **Source plan:** all-shortcuts-editable
- **Applies to:** wrangle
- **Test category:** unit

Editing a binding while a built-in preset is active silently forks the active built-in to a new custom preset, switches to it, then applies the edit — so users never have to discover or click "Copy to Custom" before making their first customization.

**Behavior:**
- The `editShortcutBinding({ commandId, shortcut })` thunk in `settingsSlice.ts` reads `state.settings.shortcuts.currentPreset`. If it names a built-in preset, the thunk:
  1. Generates a unique custom preset name. Default base is `My Shortcuts`. If taken, use `My Shortcuts (2)`, `My Shortcuts (3)`, ... incrementing until free across both `builtInPresets` and `customPresets`.
  2. Dispatches `addCustomPreset({ name, bindings: { ...activeBuiltInBindings } })`.
  3. Dispatches `setCurrentPreset(name)`.
- The thunk then dispatches `updateShortcutBinding({ presetName: <now-active>, commandId, shortcut })` to apply the user's edit.
- If the active preset is already custom, the thunk skips the fork and applies the edit directly.
- The preferences UI routes all shortcut edits through this thunk.

**Acceptance criteria:**
- Given `currentPreset: 'default'`, no custom presets, calling `editShortcutBinding({ commandId: 'markdown.bold', shortcut: 'Ctrl+Alt+B' })`: after dispatch, `currentPreset` is `'My Shortcuts'`, `customPresets['My Shortcuts']` exists, and `customPresets['My Shortcuts']['markdown.bold']` is `'Ctrl+Alt+B'`.
- Given `currentPreset: 'default'`, `customPresets: { 'My Shortcuts': {...} }`: the new custom preset is named `'My Shortcuts (2)'`.
- Given `currentPreset: 'My Shortcuts'`: no fork; the binding edit is applied to the existing `'My Shortcuts'` preset.

### KBD-013: Menu IDs Equal Registry IDs

- **Status:** Active
- **Added:** 2026-04-28
- **Source plan:** all-shortcuts-editable
- **Applies to:** wrangle
- **Test category:** integration

The native menu emits the registry command ID via the `menu:command` IPC channel. The renderer dispatches via `commandMap.get(id).execute(ctx)`, eliminating the legacy hand-curated switch and divergent IDs (`file:new` vs `file.new`, `theme:light` vs `view.themeLight`, etc.).

**Behavior:**
- Each interactive node in the menu schema (`src/shared/menu-schema.ts`) carries a `commandId` matching a registry entry.
- Main's `buildItem(node, bindings, mainWindow)` resolves the click handler to `() => mainWindow.webContents.send('menu:command', node.commandId)` and the accelerator to `bindings[node.commandId]` (with `Ctrl` mapped to Electron's `CmdOrCtrl`).
- Renderer's `App.tsx` `onMenuCommand` listener calls `commandMap.get(commandId)?.execute(ctx)` with a full `CommandContext` (including `getState`, `previewSelection`, all handlers including `onOpenFolder`).

**Acceptance criteria:**
- Every `commandId` in `menuSchema` resolves via `commandMap.get(id)` (no orphan IDs).
- The menu emits no legacy IDs (`file:new`, `view:editor-only`, `theme:light`, `workspace:openFolder`, `view:split`, `view:preview-only`, `theme:dark`, `file:open`, `file:save`, `file:saveAs`).

### KBD-014: Bindable Mouse-Modifier Commands

- **Status:** Active
- **Added:** 2026-04-28
- **Source plan:** all-shortcuts-editable
- **Applies to:** wrangle
- **Test category:** unit

Commands with `bindingShape.suffix` accept a key-only binding (`Ctrl`, `Shift`, `Alt`, `Meta`); the mouse/tap action is fixed by code. The dispatcher reads the active modifier from the binding rather than hardcoding `e.ctrlKey` or `e.altKey`.

**Behavior:**
- Affected commands:
  - `view.zoomScroll` — default `Ctrl`, suffix `Scroll`. Wheel handler in `App.tsx` reads `selectModifierBinding(state, 'view.zoomScroll')` and fires `zoomIn` / `zoomOut` only when the configured modifier matches.
  - `view.moveWindow` — default `Alt`, suffix `Drag`. Window-drag is implemented declaratively via CSS `-webkit-app-region: drag`, which Electron handles at the OS level without modifier gating; the registry entry is documentation-only and does not currently rebind the OS drag behaviour. The binding remains user-editable for discoverability and future reimplementation.
  - `markdown.openFormatToolbar` — default `Alt`, suffix `Tap`. Tap detection in `App.tsx` reads the configured modifier and fires `floatingToolbarBus.openAtCursor()` on tap (press + release within 500ms with no intervening key/mouse/blur).
- `findConflicts(shortcut, bindings, excludeId, commandShape)` partitions detection by `bindingShape.suffix` so `Ctrl+B` (markdown.bold) and `Ctrl+Scroll` (view.zoomScroll) do not conflict.
- `formatKeyboardEvent(event, allowModifierOnly)` returns the bare modifier name (`Ctrl`, `Alt`, etc.) when `allowModifierOnly` is true and the event is a standalone modifier press.
- `isValidShortcut(shortcut, modifierOnly)` accepts a single bare modifier when `modifierOnly` is true.
- `ShortcutRecorder` accepts a `mode: 'chord' | 'modifier-only' | 'tap'` prop. In `modifier-only` and `tap` modes it captures via `keyup` so a held modifier-without-other-key registers as the binding.

**Acceptance criteria:**
- `findConflicts('Ctrl', { 'markdown.bold': 'Ctrl+B', 'view.zoomScroll': 'Ctrl' }, 'view.zoomScroll', cmd => commandMap.get(cmd)?.bindingShape?.suffix)` returns `[]` (different partitions).
- `findConflicts('Ctrl', { 'view.moveWindow': 'Ctrl', 'view.zoomScroll': 'Ctrl' }, 'view.zoomScroll', shapeFn)` — both commands have suffix shapes (Drag/Scroll), so they do NOT conflict (different suffixes).
- `eventMatchesModifier({ ctrlKey: true }, 'Ctrl')` returns `true`; `eventMatchesModifier({ ctrlKey: true }, 'Alt')` returns `false`; `eventMatchesModifier({ ctrlKey: true }, null)` returns `false`.
- `isValidShortcut('Ctrl', true)` returns `true`; `isValidShortcut('Ctrl', false)` returns `false` (chord mode requires a non-modifier key).

### KBD-015: New Menu-Backed Commands

- **Status:** Active
- **Added:** 2026-04-28
- **Source plan:** all-shortcuts-editable
- **Applies to:** wrangle
- **Test category:** integration

Five commands previously implemented as Electron `role` entries or hardcoded handlers gain explicit registry entries so they appear in the Shortcuts tab and command palette and become rebindable.

**Behavior:**
- `view.reload` — default `Ctrl+R`, calls `window.electron.window.reload()` → main `webContents.reload()`.
- `view.forceReload` — default `Ctrl+Shift+R`, calls `window.electron.window.forceReload()` → main `webContents.reloadIgnoringCache()`.
- `view.toggleFullscreen` — default `F11`, calls `window.electron.window.toggleFullscreen()` → main toggles `BrowserWindow.setFullScreen`.
- `app.exit` — default `Ctrl+Q`, calls `window.electron.window.close()`.
- `workspace.openFolder` — default `Ctrl+K Ctrl+O` (chord sequence), category `navigation`, executes `ctx.handlers.onOpenFolder()`.

**Acceptance criteria:**
- `commandMap.get('view.reload')`, `commandMap.get('view.forceReload')`, `commandMap.get('view.toggleFullscreen')`, `commandMap.get('app.exit')`, `commandMap.get('workspace.openFolder')` are all defined with non-null `defaultBinding`.
- Each appears in `menuSchema` with the correct `commandId`.
- `window.electron.window` exposes `reload()`, `forceReload()`, `toggleFullscreen()` matching the expected IPC channels.

## Architectural Notes

- **Escape-to-close-dialog is dialog-local, not a registry command.** Each modal/dialog component owns its own Escape handling via `keydown` listener or `onKeyDown` prop. There is no `app.closeDialog` registry entry; an Escape behavior is not centralized because dialog-specific cleanup (e.g. cancel-recording in `ShortcutRecorder`, reset-search in `CommandPalette`) varies per dialog.
- **Window-drag region is OS-mediated.** Electron's `-webkit-app-region: drag` CSS property delegates window-drag to the OS without any modifier-key gating. The `view.moveWindow` registry entry is documentation; rebinding its modifier does not currently change OS drag behaviour. Reimplementing modifier-gated drag would require intercepting mouse events in renderer or main and synthesizing window-move via `BrowserWindow.setPosition`.
- **Stale `view.themeCycle` removed.** This command referenced a non-existent `'Lightish'` theme; it had no binding, no menu entry, and no callers. Removed in the 2026-04-28 plan.
